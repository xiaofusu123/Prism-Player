# 0002 代码门禁

- 状态：已接受（**尚未落地**，落地票 #50，被 #51「恢复可复现构建」阻塞）
- 日期：2026-10-09
- 相关：`docs/markdown/代码规范.md` §1–§5、`docs/agents/triage-labels.md`

## 背景

`docs/markdown/代码规范.md` 写了 9 节规范（命名、注释、文件组织、类设计、函数长度、日志、单测、Git 工作流），但仓库里**没有任何自动检查**：

- 无 `.clang-format`、无 `.clang-tidy`、无 `.editorconfig`；
- `.git/hooks/` 里除 `*.sample` 外为空，无 `.githooks/`、无 `.pre-commit-config.yaml`；
- 无 `.github/`、无任何 CI 配置。

后果是规范纯靠自觉，且**已经失守**：`server/` 与 `vendor/` 下 6 个文件被命名为 `CmakeLists.txt`（小写 `m`），在大小写敏感的文件系统上 `add_subdirectory()` 根本找不到它们 —— 而 Server 端的目标平台恰恰是 Ubuntu。此外 `docs/markdown/代码规范.md` §8 写了「不得直接在 `main` 开发」，实际上仓库长期只有一个分支在工作。

同时有一个反向约束：**当前构建是坏的**（vcpkg 安装树里只剩 `asio`，ffmpeg/vulkan/glfw3/spdlog 等库文件已丢失；`build.sh` 是 5 行空壳；`build.bat` 的非法输入分支把预设名写成了 `windows-clang-x64-Releasee`）。在「能编译」这个前提不成立时，任何编译相关的门禁都只会得到 `--no-verify`。

## 决策

**1. 载体：本地 Git hooks，不引入 CI。**

提交 `.githooks/`（`pre-commit`、`pre-push`）+ `.clang-format` + `.clang-tidy`，用 `git config core.hooksPath .githooks` 启用。不上 GitHub Actions。

理由：CI 要跑起来需要一台能装 msys2 + clang + vcpkg 且带 `CLANG_ROOT` / `VCPKG_ROOT` 的 Windows runner，而这套环境目前只在成员本机存在；先修好本机基线、让门禁真正跑起来，比先搭一个跑不起来的 CI 更有价值。**CI 列为第二阶段**，等构建可复现之后再评估。

**2. 深度：clang-format 全量 + clang-tidy 只开 3 条规则。**

`.clang-format`：

```yaml
BasedOnStyle: LLVM
IndentWidth: 4
ColumnLimit: 100
PointerAlignment: Left
BreakBeforeBraces: Attach
NamespaceIndentation: None
AllowShortFunctionsOnASingleLine: Inline
```

`ColumnLimit: 100` 是新定的值 —— 规范 §5.1 只约束了函数 ≤100 行，从未写过行宽。

`.clang-tidy`：**只启用三条**，且都设 `WarningsAsErrors`：

| 规则 | 参数 | 对应规范 |
|---|---|---|
| `readability-identifier-naming` | 按 §1.1 / §1.2 / §1.3 配 Case（类型 PascalCase、函数与变量 snake_case、宏与常量全大写） | §1.1–1.3 |
| `readability-function-size` | `LineThreshold: 100` | §5.1 |
| `cppcoreguidelines-virtual-class-destructor` | — | §4.3 / §4.4 |

**为什么只开这三条**：clang-tidy 的注释覆盖率、魔法数字、`modernize-*` 一类规则在现有代码上会一次炸出几百条告警。门禁一旦让人「每次提交都要滚过一屏红字」，结果一定是全体加 `--no-verify`，等于没有门禁。以后**按「先加检查 → 先清零 → 再启用」逐条加**。

**3. pre-commit 与 pre-push 的职责划分。**

- `pre-commit`：对 staged 的 `*.c` / `*.cpp` / `*.h` 跑 `clang-format --dry-run --Werror`；再加一条「文件名不得为 `CmakeLists.txt`」的防回归检查（见 #52）。
- `pre-commit` **不跑 clang-tidy**：它需要 `compile_commands.json`（当前构建是坏的，拿不到），而且慢到开发者会直接绕过。
- `pre-push`：只要求 `cmake --build --preset windows-clang-x64-Debug` 成功。**不跑 `ctest`**（列第二阶段）、**不跑 Release 预设**（耗时翻倍而收益低）。耗时上限等 #51 恢复构建后实测再填。

**4. 安装方式**：提交 `scripts/install-hooks.ps1`，内容即 `git config core.hooksPath .githooks`；并把这一步写进 `AGENTS.md` 的前置条件，让新克隆能一次配好。hook 脚本统一用 `#!/bin/sh`，由 Git for Windows 自带的 bash 执行，**不依赖 cmd 或 PowerShell**（成员机器上 cmd 与 Git Bash 的行为不一致，这是最容易踩的坑）。

**5. 允许 `--no-verify`，但限一种情况**：格式批量整理（例如初次引入 clang-format 时的一次性重排）需要单独一次提交、与本就是一次性的提交合并会污染历史。使用者必须在 PR 描述里说明这次跳过了什么。日常提交不允许。违规靠 PR 审查拦 —— 这也是为什么 §8 的「合并前须提交合并申请并代码审查」必须真的执行。

**6. 工具版本钉死为 `22.1.8`**。`clang-format` / `clang-tidy` 只要版本不同，格式化结果就会在成员之间来回抖动（A 格式化、B 提交时又改回去）。hook 的第一件事就是比对版本前缀，不匹配直接报错退出。`CMakePresets.json` 已经依赖机器级的 `CLANG_ROOT`（默认 `D:\Program\App\msys64\clang64\bin`），版本钉死在同一个变量背后。

## 后果

**正面**：格式与三条最硬的规范变成可机检；`CmakeLists.txt` 这类平台相关错误不再靠人去 Ubuntu 上才发现。

**负面 / 已知缺口**：

- **表达不了的部分仍然靠自觉**：clang-format 管不到命名、扩展名（规范 §3.1 禁用 `.cc`/`.hpp`）、目录结构、Doxygen 注释格式、类设计、单元测试存在性。这些没有工具能拦。
- clang-tidy 三条规则的**首次全量扫一定会报错**（现有代码基本没人按 §1 命名）。启用前必须完成一次基线清零，这也是「先清零后开门禁」的原因。
- `pre-push` 挡在 push 前面意味着**推送前必须能完整构建**，开发者本地改了一半就推不了 —— 这是刻意的，但会在构建本来就慢的时候被抱怨。
- **覆盖率 >80%（§7）不进门禁**。它是 PR 审查的期望值，不是阻断条件（理由见 #43 的结论：真正有实现的代码只有三处，硬卡覆盖率只会逼出形式化的空测试）。

## 备选方案

- **GitHub Actions CI**：对多平台（尤其是 Server 的 Ubuntu 目标）更有说服力，且无法被 `--no-verify` 绕过。放弃于第一阶段的原因是仓库当前构建不可复现，CI 会长期一片红，反而让人学会忽略它。第二阶段重新评估。
- **`pre-commit` 框架（Python）**：生态成熟、hook 管理方便。放弃原因是它要求每个成员装 Python 环境，而这个项目的工具链已经够重（MSYS2 + clang + vcpkg + Flutter）。
- **只靠 code review 不设门禁**：仓库长期只有一个人在工作，review 事实上是自审，没有第二双眼睛能兜住格式漂移。
- **全量 clang-tidy（`modernize-*` + `cppcoreguidelines-*` 全套）**：一次引入几百条告警，必然被绕过，见决策 2。
- **把 ctest 放进 `pre-push`**：等 `test/` 恢复、全量测试耗时可测之后再决定（#43 / #54）。
