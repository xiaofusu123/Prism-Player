# 0001 分层架构与库形态

- 状态：已接受
- 日期：2026-10-09
- 相关：`docs/markdown/设计文档.md` §2.1、`docs/markdown/项目框架.md` §2

## 背景

PrismPlayer 是跨平台（Windows / Android / Linux，计划 iOS）音视频播放器，同时要支持联机同步播放。这带来两个相互拉扯的约束：

1. **UI 用 Flutter 写**，C++ 侧必须能被 Dart 通过 FFI 调用；
2. **Server 端要复用同一套协议与业务概念**（房间、信令、账号），不能让客户端逻辑锁死在 UI 里。

项目从一开始就按六层目录搭了起来（`client/` 下 `adapter` / `engine` / `business` / `service` + `ui/` 的 FFI 目录），但**没有在任何地方记下「为什么是六层」和「为什么某些层是动态库、某些是静态库」**。这份 ADR 把它固定下来。

## 决策

**六层，自上而下**：

| 层 | 目录 | 职责 |
|---|---|---|
| 表示层 UI | `ui/`（Flutter/Dart） | 界面与交互 |
| FFI 桥接层 | `ui/lib/ffi/` | Dart ↔ C++ 的动态库加载与函数绑定 |
| 服务层 Service | `client/service/` | 对外 C API 门面（`_API` / `extern "C"`） |
| 业务层 Business | `client/business/av_sync/`、`client/business/network/` | AV Sync 与 Network |
| 引擎层 Engine | `client/engine/` | 音频、视频引擎（工厂 + 平台实现） |
| 适配器层 Adapter | `client/adapter/` | 文件、数据库、网络、配置、加密 |

**库形态**：

| CMake 目标 | 形态 | 层 |
|---|---|---|
| `client-adapter` | `STATIC` | Adapter |
| `client-engine` | `SHARED` | Engine |
| `client-av_sync` | `STATIC` | Business（AV Sync） |
| `client-network` | `STATIC` | Business（Network） |
| `client-service` | `SHARED` | Service |
| `Prism-server` | `EXECUTABLE` | Server |

**理由**：

- Service 与 Engine 编 `SHARED`，是因为**它们要跨语言边界**：Flutter 侧只需要加载 `libclient-service.dll` 一个文件（`ui/lib/ffi/ffi_bridge.dart` 拼的就是它的路径）。若全是静态库，Dart 侧就要链一大坨，且无法在不重编 UI 的情况下替换。
- Adapter 与 Business 编 `STATIC`，是因为**它们是纯实现细节**，没有跨语言或插件化需求，静态链接才能让编译器做内联与去虚化。
- 每层内部一律 `include/`（对外声明）+ `internal/`（本层私有）+ `src/`（实现）三层，配套规范 §3.2。

## 后果

**正面**：

- 每层可以独立编译与测试；`client-service` 的 32 个 C API 是唯一的跨语言契约，UI 与 C++ 可以并行开发。
- Server 端可以复用 Business 层的概念（房间、信令）而不必拖上 UI 与编解码。
- Adapter 的静态链接让「基础设施」调用点能内联，符合它被高频调用的定位。

**负面 / 需要注意**：

- **Adapter 是静态库，而 Engine 与 Service 是动态库** → Adapter 的实现会在两个 `.dll` 里各有一份。任何放在 Adapter 里的**全局状态（单例、缓存、句柄表）都不会跨 dll 共享**。目前 Adapter 是空壳所以没暴露，实现时要么避免全局状态，要么把它上提到 Service 层。
- 六层的**概念边界与真实依赖曾经不一致**：`client/business/network/CMakeLists.txt` 曾把 `client-engine` 声明为 `PRIVATE` 依赖，而 Network 并不需要引擎。已立案修正（#52）。
- **绝大多数层目前是空壳**：真正有实现的只有 Business 的 AV Sync（323 行）、Service 门面（`Player.cpp` 448 行）与 `vendor/threadpool`。Adapter / Network / Engine 解码 / Server 都还是 0 字节或只有声明。**本 ADR 记录的是形态决策，不是完成度。**

## 备选方案

- **单体静态库**：实现最简单，编译最快。放弃原因是 Flutter 侧必须链进整个 C++ 运行时，且换一个后端要重编 UI。
- **全动态库（含 Adapter）**：跨 dll 传递 C++ 对象（`std::string` / `std::unique_ptr`）在 Windows 上会撞 CRT 边界问题，需要额外的 C 风格边界层，代价大于收益。
- **三层（UI / C++ / Server）**：不足以承载「Service 给二次开发暴露公共 API」这个目标（见 `项目框架.md` §2.3），也不足以让 AV Sync 与 Network 独立推进。
- **不分层，按功能切模块**：会让「谁依赖谁」变成隐式的，正是当前 `client-network` 误依赖 `client-engine` 这类问题会持续发生的土壤。
