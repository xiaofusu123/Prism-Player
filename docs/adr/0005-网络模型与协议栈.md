# 0005 网络模型与协议栈

- 状态：已接受（**仅设计，尚未实现**）
- 日期：2026-10-09
- 相关：`docs/markdown/设计文档.md` §5.2、`client/business/network/include/`、`server/`

## 背景

联机播放需要的网络能力分三类，量级与延迟要求完全不同：

1. **实时信令** —— 加入/离开房间、播放/暂停/seek 的同步指令。量小、延迟敏感、需要服务端主动推送；
2. **REST 式请求** —— 登录、房间列表、账号信息。量大、延迟不敏感、请求-响应模式；
3. **P2P 文件直传** —— 房间内共享媒体文件。量大、耗时长。

同时 **Server 端的运行平台是 Ubuntu**（客户端是 Windows/Android/iOS），所以网络层的选型不能是 Windows 专有的（`IOCP`、`WSAEventSelect`）。

`设计文档.md` §5.2 给出的分析来自当时的方案评审；该文档 2026-06-10 曾被删除、现已恢复（见 #0003）。

## 决策

**1. 并发模型：ASIO 异步 I/O（单线程事件循环），不用「同步 I/O + 线程池」。**

```
同步 + 线程池：               ASIO 异步：
[Thread1] → 等待 → 回调      [单线程 EventLoop]
[Thread2] → 等待 → 回调      ├── Socket1 ready
[Thread3] → 等待 → 回调      ├── Socket2 ready
浪费线程资源                  └── Timer event
```

核心理由是 **C10K 问题**：面向大量并发连接时，单线程异步模型在内存与 CPU 上的效率远超「一连接一线程」的同步模型。本项目虽然达不到 C10K 规模，但 Server 同时承载多个房间、每个房间多个成员的长连接，模型选择的收益方向是一致的。

**2. 协议与库的对应关系**：

| 协议 | 用途 | 库 |
|---|---|---|
| WebSocket | 实时信令（加入/离开房间、播放控制） | `ixwebsocket` |
| HTTP | REST API（登录、房间列表） | `asio` |
| P2P | 文件直传（**计划中**） | `asio` |

WebSocket 因为需要「服务端主动推送 + 心跳 + 断线重连」，交给 `ixwebsocket`（它本身就建在 asio 上）；HTTP 与将来的 P2P 直接用 `asio`。

**3. 客户端网络层的接口边界**（`client/business/network/include/`）：

`IAccountManager`（账号）、`IRoomManager`（房间）、`ISignalingClient`（信令）、`INetworkObserver`（事件回调）、`NetworkFactory`（工厂）、`NetworkTypes`（公共类型）。

服务层通过 `client/service/internal/IServiceNetwork.h` 这个抽象接口使用它们，当前挂着默认桩实现 —— 这样 Service 层的 32 个 C API 可以在网络模块缺席的情况下先跑通。

## 后果

**正面**：

- 一套 asio 覆盖 HTTP 与将来的 P2P，不引入第二套 I/O 框架。
- 异步模型让「超时、重连、心跳」这类定时逻辑可以挂在同一个事件循环里，不需要额外的定时线程。
- 服务层已经通过 `IServiceNetwork` 抽象与网络实现解耦，两边的进度互不阻塞。

**负面 / 需要注意**：

- **网络模块目前是「占位」状态：接口已定义，无实现。** `client/business/network/include/` 下 6 个头文件是真的（39/41/42/40/22/65 行），但 `internal/NetImpl.h` 与 `src/tmp.cpp` 都是 **0 字节**。`ixwebsocket` 与 `asio` 已在 `vcpkg.json` 声明，无 `find_package` 消费，磁盘上没有任何 socket 代码。
- **Server 端一行逻辑都没有**：`server/main.cpp` 只有 `int main(){ return 0; }`，`server/{adapter,business,network}/` 各层只有 0 字节的 `tmp.h`/`tmp.cpp`。协议、表结构、时序都还没落到代码。
- **协议细节尚未定义**：消息格式（JSON schema？）、信令时序（谁先发？）、时钟同步（跟随者如何把本地时钟对齐到房主？）、错误码映射（`PRISM_ERROR_NETWORK` 之下的细分）—— 这些都不在选型范围内，但决定了实现量。
- 异步回调模型**对调试不友好**：调用栈断裂，出问题要靠日志（规范 §6 要求的 spdlog 输出在这里尤其重要）。
- `ixwebsocket` 相对主流的 `websocketpp` 社区更小。

## 备选方案

- **`websocketpp`**：更主流、文档更多。它曾被写在 `项目计划书.docx` 里（2026-06-01 冻结的 Word 旧版），后来在 md 中改为 `ixwebsocket`。放弃原因是 `websocketpp` 与 Boost.Asio 版本耦合较紧、编译期模板重量大，而 `ixwebsocket` 自带 asio 且更轻。
- **同步 I/O + 线程池**（复用 `vendor/threadpool`）：实现直观、调试简单，也是 `vendor/threadpool` 存在的隐含理由。放弃原因是「一连接一线程」在成员数与房间数增长时线性吃内存，且线程上下文切换的成本在这个 I/O 密集的场景里没有收益。
- **gRPC / 消息队列**：为跨服务通信提供现成的 schema 与流控。放弃原因是本项目是「客户端 ↔ 单个自建 Server」，且客户端是 C++ 与 Flutter，引入 gRPC 会同时拖进 protobuf 代码生成与两套运行时。
- **只用 HTTP 长轮询，不引入 WebSocket**：实现最简单。放弃原因是房间内的播放控制需要**低延迟双向推送**，长轮询的延迟与空转开销都不可接受。
- **纯 P2P（无中心 Server）**：省掉服务端。放弃原因是房间发现、成员列表、以及「房主掉线怎么办」这些状态必须有裁决者，最终还是要一个中心的 Server。
