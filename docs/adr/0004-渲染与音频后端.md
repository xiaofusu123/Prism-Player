# 0004 渲染与音频后端

- 状态：已接受（**仅设计，尚未实现**）
- 日期：2026-10-09
- 相关：`docs/markdown/设计文档.md` §3.1 / §3.2（含完整选型对比表）、`docs/markdown/代码规范.md` §9

## 背景

播放器的两个核心后端需要选型：**视频渲染 API** 与 **音频输出 API**。约束来自项目目标本身：

- 平台目标是 **Windows / Android / Linux 三端**（iOS 在计划内），所以后端方案必须能覆盖这三家；
- 音视频同步（AV Sync）要求**低延迟**且**能拿到精确的时钟**，否则同步算法没有可用的时间基准；
- 解码统一走 **FFmpeg**（`vcpkg.json` 的 `client` feature 已声明 `ffmpeg`），可变速率播放用 **SoundTouch**。

这一节的大部分分析来自 `docs/markdown/设计文档.md`（该文档 2026-06-10 曾被删除，现已恢复，理由见 #0003）。

## 决策

**视频：Vulkan。**

| 方案 | 性能 | 跨平台 | 学习曲线 | 选定 |
|---|---|---|---|---|
| **Vulkan** | 极高 | ✅ Windows / Android / Linux | 高 | ✅ |
| DirectX 12 | 极高 | ❌ 仅 Windows | 中 | ❌ |
| OpenGL | 中 | ✅ | 低 | ❌ |
| Metal | 极高 | ❌ 仅 Apple | 中 | ❌ |

Vulkan 是**唯一同时覆盖 Windows、Android、Linux 三大平台的现代 GPU API**；显式资源管理（`VkImage` → 纹理上传）也让视频帧的低延迟渲染更可控。

**音频：WASAPI 共享模式（Windows）。**

| 方案 | 延迟 | CPU 占用 | 独占性 | 选定 |
|---|---|---|---|---|
| WASAPI Exclusive | 极低 | 低 | 独占设备 | ❌ |
| **WASAPI Shared** | 低 | 低 | 与系统混音 | ✅ |
| DirectSound | 高 | 低 | 共享 | ❌ |
| WaveOut | 极高 | 低 | 共享 | ❌ |

Exclusive 模式延迟最低，但会**独占音频设备** —— 用户在播放时听不到系统通知音，这对一个桌面播放器是不可接受的体验代价。共享模式在延迟与兼容性之间取得平衡，而延迟差距对本项目的同步算法（阈值在几十毫秒量级）不构成约束。

**跨平台扩展路径**：通过工厂模式扩展 `AudioEngineAAudio`（Android）/ `AudioEngineAudioUnit`（iOS/macOS），抽象接口 `AudioEngineFactory` 不变。

**解码管线**（`设计文档.md` §3.2 原样保留）：

```
MP4/MKV → FileAdapter → FFmpeg Demuxer
  ├── 视频流 → FFmpeg Video Decoder → AVFrame → Vulkan Texture Upload → GLFW Window Render
  └── 音频流 → FFmpeg Audio Decoder → PCM Buffer → SoundTouch（变速变调）→ WASAPI 输出
```

## 后果

**正面**：

- 一套渲染代码覆盖三端，不需要为 Android 再写一份 OpenGL ES 路径。
- 共享模式不会因为播放器抢占设备而惹恼用户。

**负面 / 需要注意**：

- **这套东西目前一行都没实现。** 磁盘上只有骨架：`client/engine/src/AudioEngineWasapiShared.cpp`（29 行）、`AudioEngineWasapiSharedFactory.cpp`（7 行）、`VideoEngineVulkan.cpp`（32 行）、`VideoEngineVulkanFactory.cpp`（7 行）。**没有任何真实的 WASAPI 或 Vulkan 调用**，`client/engine/src/` 下也**没有任何 FFmpeg 相关源文件**。本 ADR 记录的是选型决策，不是完成度。
- **Vulkan 的学习曲线是本项目最陡的一处**：初始化、物理设备选择、交换链、命令缓冲、同步原语这一整套样板代码远超其它后端。这是选它的已知代价。
- **依赖声明与消费脱节**：`vcpkg.json` 的 `client` feature 已声明 `ffmpeg` / `vulkan` / `glfw3` / `soundtouch` / `glm`，但**全仓没有一处 `find_package` 去消费**。也就是说现在是「装了但没接线」。
- WASAPI 的**设备热插拔**（切换默认输出设备）在共享模式下需要 `IMMDeviceEnumerator` 通知回调，方案里没有提，实现时会遇到。
- 同步算法依赖音频时钟的准确 `current_pts`。「共享模式延迟略高于独占」这一点会体现在 `ahead_threshold_ms` / `behind_threshold_ms` 的取值上，阈值需要在真机上实测标定，不能照抄设计稿。

## 备选方案

- **DirectX 12 / Metal**：性能同级，但直接把项目锁死在单一平台，与「跨三端」的目标冲突。
- **OpenGL**：学习曲线最低、生态最成熟，但已被 Khronos 列为遗留 API，在移动端（Android）的驱动支持也在退化；选择它等于现在就接受一次未来的迁移。
- **WASAPI Exclusive**：延迟最优，适合专业音频，但独占设备对普通播放器是体验倒退。
- **SDL2 / miniaudio 之类的跨平台音频抽象**：可以用一套 API 覆盖三端音频，省掉 WASAPI/AAudio/AudioUnit 三份实现。放弃原因是它们对**精确音频时钟**的暴露程度不如直接用平台 API，而时钟正是 AV Sync 的命脉。
- **libplacebo 直接做渲染/色调映射**：`设计文档.md` §10 把它列为 HDR 的扩展方向。它建立在 Vulkan 之上，与主方案不冲突，只是暂不引入。
