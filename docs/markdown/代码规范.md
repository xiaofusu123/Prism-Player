## 1. 命名规范

### 1.1 类名、结构体名、枚举名、文件名

使用 **驼峰命名法** (PascalCase)，首字母大写。

```cpp
// 正确
class AudioEngine { };
struct AudioSyncInfo { };
enum class SyncState { };

// 错误
class audio_engine { };
struct audio_sync_info { };
```

> **沿革**：2026-06-06 之前本规范与 2026-05-25 冻结的 `代码规范.docx`（已归档至 `docs/archive/`）都曾规定**文件名用蛇形命名法**，后改为 PascalCase。以当前规范为准 —— 代码实测一致：`client/`、`practice/` 下 55 个 `.h/.cpp` 中 51 个是 PascalCase，仅 `pch.h`、`tmp.*` 等 4 个例外。

### 1.2 函数名、变量名

使用 **蛇形命名法** (snake_case)，全小写加下划线。

```cpp
// 正确
bool set_play_speed(float speed);
int student_age;
void init_audio_engine();

// 错误
bool setPlaySpeed(float speed);
int studentAge;
void initAudioEngine();
```

### 1.3 宏、常量

使用 **全大写 + 下划线**。

```cpp
#define MAX_SIZE 1024
#define PI 3.14159

const int DEFAULT_PORT = 8080;
```

### 1.4 命名空间

使用 PascalCase，项目根命名空间为 `Prism`，子命名空间按模块划分。

```cpp
namespace Prism::Engine { }
namespace Prism::Business { }
namespace Prism::Service { }
namespace Prism::Server { }     // Server 端代码
```

> ⚠️ 目前 `server/` 下还没有任何非空 C++ 逻辑，`Prism::Server` 是为 Server 端实现预留的命名空间，**尚未有代码使用**。

### 1.5 简写约定

使用大众熟知和默认约定的简写，不自行创造。

```cpp
// 正确（公认简写）
int max_size;      // maximum
int user_id;       // identifier
uint64_t pts;      // presentation timestamp

// 错误（自创简写）
int mx_sz;
int usr_idfr;
```

## 2. 注释规范

### 2.1 API 接口注释

使用 **Doxygen 风格**（类似 JavaDoc），函数或复杂设计必须在前面添加注释。

```cpp
/**
 * @brief 音频跳转
 * @param pts 跳转的时间戳（毫秒）
 * @param seek_mode 跳转模式。0 为绝对模式，pts 为非负值；1 为相对模式
 * @return 跳转成功返回 true，失败返回 false
 */
virtual bool seek(uint64_t pts, int seek_mode) = 0;
```

### 2.2 结构体成员注释

```cpp
/**
 * @struct AudioSyncInfo
 * @brief 音频同步信息
 */
struct AudioSyncInfo {
    std::atomic<uint64_t> current_pts{0};  /**< 当前音频帧解码时间戳（ms） */
    std::atomic<uint64_t> next_pts{0};     /**< 下一帧音频解码时间戳（ms） */
    std::atomic<uint32_t> start_time{0};   /**< 流开始的时间 */
};
```

### 2.3 枚举注释

```cpp
/**
 * @enum SyncState
 * @brief 音频同步状态
 *
 * - UNINIT: 音频引擎未初始化
 * - CALIBATING: 音频校准中
 * - SYNCHRONIZED: 音频已同步
 * - AHEAD: 音频时间超前
 * - BEHIND: 音频时间滞后
 * - DISABLE: 未启用同步控制
 * - SYNC_ERROR: 错误状态
 */
enum class SyncState {
    UNINIT,
    CALIBATING,
    SYNCHRONIZED,
    AHEAD,
    BEHIND,
    DISABLE,
    SYNC_ERROR
};
```

## 3. 文件组织

### 3.1 后缀名

C/C++ 文件统一使用：
- **源文件**：`.cpp`
- **头文件**：`.h`

不使用 `.cc` 和 `.hpp`。

### 3.2 目录结构

每个模块遵循三层目录结构：

```
module/
  include/     -- 公开接口头文件（抽象接口、工厂接口、公共类型）
  internal/    -- 平台实现（impl 细节，不对外暴露）
  src/         -- 源文件
```

**同一个东西在 `include/` 与 `internal/` 下的名字通常不同**：`include/` 放抽象接口（如 `DBAdapter`、`CryptoAdapter`），`internal/` 放平台实现（如 `SQLiteDBAdapter`、`OpenSSLCryptoAdapter`）。这不是命名不一致，不要「统一」掉。完整对照表见根目录 `GLOSSARY.md`。

示例 (`client/engine/`)：

```
engine/
  include/
    AudioEngine.h              -- 抽象接口
    AudioEngineFactory.h       -- 工厂接口
    VideoEngine.h
    VideoEngineFactory.h
  internal/
    AudioEngineWasapiShared.h  -- Windows 平台实现
    VideoEngineVulkan.h        -- Vulkan 平台实现
  src/
    ... (源文件)
```

### 3.3 预编译头

`pch.h` 放在 `common/` 目录，供全局使用。

## 4. 类的设计

### 4.1 成员排列顺序

- **public** 公共成员（公开接口）放在前面
- **private** 私有成员放在后面

```cpp
class AudioEngine {
public:
    virtual bool init() = 0;    // 前面
    virtual bool play() = 0;
    // ...

protected:
    // protected 成员

private:
    // private 成员在最后
};
```

### 4.2 函数定义位置

- 头文件中：仅放声明
- 源文件中：放定义体
- **例外**：模板函数定义须在头文件中实现
- **例外**：简单的 getter 函数（如获取成员变量）可放在类内部

```cpp
// header 中
class VideoEngine {
public:
    int get_width() const { return width; }  // getter 可内联
    virtual bool init() = 0;                  // 声明
};

// src 中
bool VideoEngineVulkan::init() {
    // 定义体
}
```

### 4.3 继承深度限制

如果类的继承超过 **3 代及以上**，应改为类的组合或聚合。

### 4.4 设计原则

类设计必须遵循三大原则：
1. **单一职责原则**：每个类只负责一项功能
2. **开放封闭原则**：对扩展开放，对修改封闭
3. **里氏替换原则**：子类必须能替换父类

### 4.5 构体成员初始化

Struct 成员变量应在结构体内部初始化，默认值尽量为 `0`，**不得重载**结构体的构造函数。

```cpp
// 正确
struct AudioSyncInfo {
    std::atomic<uint64_t> current_pts{0};
    std::atomic<uint64_t> next_pts{0};
    std::atomic<uint32_t> start_time{0};
    std::atomic<uint64_t> duration{0};
};

// 错误 — 不要重载 struct 构造函数
struct AudioSyncInfo {
    AudioSyncInfo() { ... }  // 禁止
};
```

### 4.6 虚析构

**多态基类必须声明虚析构函数**（`virtual ~Base() = default;`）。否则通过基类指针删除派生对象时行为未定义。

```cpp
// 正确
class VideoEngine {
public:
    virtual ~VideoEngine() = default;
    virtual bool init() = 0;
};

// 错误 — 有纯虚函数却没有虚析构
class VideoEngine {
public:
    virtual bool init() = 0;
};
```

> 本条由 `cppcoreguidelines-virtual-class-destructor` 强制（见 §0），是规范里唯一一条**新增**的类设计硬约束 —— 它原先不在本规范中，但代码里已经普遍遵守（`VideoEngine`、`AudioEngine` 等都有 `virtual ~...() = default;`），现在把它写下来。

## 5. 函数规范

### 5.1 函数长度

一个函数的代码量**不要超过 100 行**，每个函数应只有单一的功能。

> 由 `readability-function-size`（`LineThreshold: 100`）强制。

### 5.2 API 设计

- 正式编写代码前，优先设计好公共 API 并提交到主分支合并
- 合并后 API 如有变动，须通知所有人
- API 接口设计好后尽量不要变动

## 6. 日志

重要逻辑部分需要输出日志，以方便后续调试。

使用 **spdlog** 日志库进行日志输出。

```cpp
#include <spdlog/spdlog.h>

spdlog::info("Audio engine initialized");
spdlog::warn("Buffer underrun detected");
spdlog::error("Failed to open file: {}", filename);
```

> `spdlog` 是目前唯一**真的被代码用上**的第三方库：`client/service/src/Player.cpp:11` 与 `client/business/av_sync/src/` 的 4 个 `.cpp` 都 include 了它。其余依赖见 `项目计划书.md` §4。

## 7. 单元测试

- 模块完成后须编写单元测试
- 测试统一放在 **`test/`** 文件夹中，**按模块分子目录**：

  ```
  test/
    av_sync/          # 对应 client/business/av_sync/
    service/          # 对应 client/service/
    threadpool/       # 对应 vendor/threadpool/
  ```

  每个子目录一个 `CMakeLists.txt`；根 `test/CMakeLists.txt` 只负责 `add_subdirectory(<模块>)`。
- 命名格式：`模块名_test`
- 使用 **GTest** 框架（来自 vcpkg 的 `test` feature，`find_package(GTest CONFIG REQUIRED)`）
- 单元测试覆盖率**目标为 80%**，但**这是期望值，不是门禁的阻断条件**

```cpp
// test/av_sync/sync_algorithm_test.cpp
#include <gtest/gtest.h>
#include "SyncAlgorithm.h"

TEST(SyncAlgorithmTest, DetectDrift) {
    // ...
}
```

> **为什么覆盖率不进门禁**：仓库里真正有实现的代码只有三处（`av_sync` 323 行、`Player.cpp` 448 行、`threadpool` 196 行），硬卡 80% 只会逼出「为了覆盖率而写」的空测试。改为**按模块分批推进、在 PR 审查里作为期望值**：① AV Sync → ② Service（`Player.cpp` 的 32 个 C API）→ ③ ThreadPool。
>
> **§7 的现状**：`test/` 目录当前**为空**。2026-06-03 的 `f9ddd15`（`remove test cache`）删掉了 781 行测试（4 个测试文件 + `CMakeLists.txt`）。恢复与补写计划见 #54。
>
> **沿革**：`代码规范.docx`（2026-05-25 冻结，已归档）写的是「统一放在 `tests` 文件夹」——那是复数，与实际目录 `test/`（单数）不符，以本节为准。

## 8. Git 工作流

- 开发时**新建分支**进行开发，**不得直接在 main 分支上开发**
- 合并到 main 分支前需提交合并申请（Pull Request）并进行代码审查
- 代码审查中如不符合以上规范则打回修改

```
main
  |
  +-- feature/audio-decoder    (开发分支)
  +-- feature/network-module   (开发分支)
  +-- fix/seek-bug             (修复分支)
```

**当前执行方式（照实记）**：

- 仓库目前只有 **@xiaofusu123 一名 admin**，其他成员虽在 collaborators 中但尚无提交。
- **GitHub 不允许 PR 作者请求自己 review**，所以单人开发时 PR 实际是**自审自合**：仍然开 PR、仍然写「做了什么 / 为什么 / 不包含 / 审查」四节，但没有人会独立复审。这是当前的事实，不是规范允许的做法。
- 因此「合并前须代码审查」这条**现在无法真正满足**。等有多人同时在提交后恢复互审，并考虑引入 `CODEOWNERS` 做强制指派。
- 门禁（§0）落地后会承担一部分原本靠审查拦的工作（格式、命名、函数长度、文件名大小写）。即便如此，**门禁只是底线，不是审查的替代**。
